# New API 生产级多厂商配置手册（实战版）

> 来自一套真实跑了数月的多厂商免费 API 网关：多入口级联、看门狗自动巡检、
> 告警推送、备份体系。本文是踩坑换来的完整思路，示例全部脱敏。

## 0. 总体架构

```
你的程序 ──统一模型名──> 主 New API 网关 ──┬--> 免费厂商 A（多账号）
                                          ├--> 免费厂商 B
                                          └--> 级联：另一台 New API（异地出口）
                                                └--> 更多厂商
```

- **统一模型名**：程序只认 model-1/model-2 这类自定名，对号表决定实际厂商；
- **级联**：主网关把某厂商配成指向另一台 New API 的渠道——异地出口能绕开
  「某模型从某些 IP 出口就卡死」的地域问题（见 §5）；
- **配置即文件**：渠道/映射全部沉淀为 routing.yaml 版本化，改配置=改文件+下发，可回滚。

## 1. 鉴权与会话治理（最容易翻车的地方）

| 事项 | 结论 |
|---|---|
| 账密会话 | **15 分钟过期**；每次登录在服务端留一条**永不回收**的会话行；上限 50 条，约 17 小时塞满后**所有自动化 409 静默失败**（我们曾停摆 30 小时才定位到） |
| 正确姿势 | **PAT 优先**（创建配方见 02 篇）；PAT 不可用时用 refresh cookie 轮换**同一**会话行（不新增）；登录只作最后兜底 |
| 会话清理 | 只有当会话数超过阈值（如 >20）才 revoke-others——两个脚本若每轮都清，会**互相踢下线**、每轮 401 重登，形成风暴 |
| 面板令牌的坑 | 创建需「安全验证」（password → proof_token → 带 X-Security-Proof 头），流程无公开文档，见 02 篇 |

## 2. 渠道编排

- **层级下探**：main → backup → low 依次兜底；**同档不互兜**（会循环重试放大故障）；
- **状态码映射**：上游 429 映射成 503，让网关把它当「该渠道不可用」而不是「请求失败」，自动换下一家；
- **账号×模型粒度**：每账号×每模型一条独立渠道——出问题一眼定位到「哪家哪号哪个模型」；
- **param_override 的坑**：带参数覆盖的渠道会污染请求级 header 快照，导致同请求后续渠道的 header 覆盖失效——能用模型映射解决就别用 header 覆盖；
- **镜像钉摘要**：网关镜像按 digest 钉死，不要 :latest——rc 版本之间行为差异能要命。

## 3. 看门狗（自动禁用/复活）设计要点

1. **判据用错误日志，不用「渠道测试」**——实测测试失败不写错误日志；
2. 阈值制：如 10 分钟窗口内 3 次失败才动手，单次失败别乱禁；
3. **禁用必须用 status=3（自动禁用）**，与人工的 2 区分——审计链完整，复活只认「自己禁的」；
4. **人工禁用的永不被自动复活**（面板上手动停的渠道 = 用户显式决定）；
5. 复检退避（30 分钟 ×2）防抖动；「某别名下可用渠道数为 0」「禁用超时未恢复」都要告警；
6. 告警**不许吞通知**：失败也要推出来（如 Telegram），配 OnFailure 兜底；
7. 多实例脚本加文件锁（flock）单实例化，状态文件原子写。

## 4. 两个真实案例（为什么这些设计是必须的）

**案例一：不报错的慢死。** 某免费账号×某模型组合，24 小时内 6/6 请求挂死（单次 700-950 秒），**HTTP 200 正常返回不报错**——重试逻辑、自动禁用全都不触发，请求只是无限等。结论：这类「失败却自报成功」只能靠**人工把它移出候选**，并给所有请求加超时上限。

**案例二：出口决定生死。** 同一把 key、同一模型、同一请求体：从 A 出口 6/6 卡死，从 B 出口 6/6 正常（0.7-4.4 秒）。卡点是「**模型 × 出口 IP × 时段**」三维问题。教训：**禁止单模型单轮次测试就给某个出口判死刑**，也说明级联/多出口不是可选项是刚需。

## 5. 安全与运维

- **关注册**：公网暴露的网关必须关掉开放注册（实测裸奔两天被自动注册出 11 个用户）；
- **会话刷满事故的归因**：来源 IP 在链路有 NAT 时**不能区分自己人/外部**，判据要看 UA + 请求模式；
- **口令轮换**有安全验证流程（password → proof_token → PUT 自身），同样无公开文档，思路同 PAT 的 proof 机制；
- **备份**必须覆盖 routing.yaml 与脚本本体；备份目录校验非空 + 严格权限（umask 077）；
- 配置保鲜：定时检查配置陈旧度（staleness），防「改了没下发」的假状态。

## 6. 速查：实测踩坑总表

| 坑 | 一句话结论 |
|---|---|
| 账密做自动化 | 17 小时必死，用 PAT |
| 改渠道带 status | 服务器硬拒，永不带 |
| status=3 | 系统保留（自动禁用），人工只能发 1/2 |
| 建渠道 body | 包裹 `{"mode":"single","channel":{...}}`；改是扁平+id |
| 渠道 key | 响应永不回显 |
| 渠道测试按钮失败 | 不写错误日志，看门狗看不见 |
| 单模型单轮测出口 | 三维问题，别急着下结论 |
| 同档重试互兜 | 循环放大故障，按档位下探 |
