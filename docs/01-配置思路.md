# 多厂商配置思路：统一模型名 + 层级兜底 + 看门狗

## 核心问题

免费 API 厂商注册了一堆：每家送不同的额度、支持不同的模型、稳定性参差不齐。
在 New API 里逐个手工建渠道，结果往往是：渠道几十条、模型名五花八门、一家挂了全站报错、出问题不知道查哪条。

## 三层设计

### 1. 统一模型名（对号表）

你的程序永远只请求 `model-1`、`model-2` 这类**你自己定的名字**，
由一张「统一模型名 → 厂商真实模型」的对照表决定实际打到哪家：

| 统一模型名 | 厂商 | 厂商真实模型 | 层级 | 权重 |
|---|---|---|---|---|
| model-1 | 厂商A | their-fast-model | main 主力 | 100 |
| model-1 | 厂商B | glm-fast | backup 备用 | 50 |

好处：换厂商/换账号**只改表，不改程序**；同一名字可挂多条，按层级依次兜底。

### 2. 层级 + 权重

- **main 主力**：额度大/速度快的优先跑；
- **backup 备用**：主力失败自动下探；
- **low 垫底 / junk 不用**：压箱底和已废的。
- 同层级内按权重分流；**重试按档位下探，同档不互相兜底**（实测：同档互兜会造成循环重试放大故障）。

### 3. 看门狗（巡检 + 自动禁用/复活）

- 按 New API **错误日志**判定（不是渠道测试按钮——实测：测试失败不写错误日志！）；
- 窗口内失败满阈值（建议 3 次/10 分钟）→ 自动禁用，**必须用 status=3（自动禁用）而非 2（手动禁）**，
  这样审计链完整：看门狗禁的看门狗复活，人工禁的永不被自动复活；
- 加复检退避（如 30 分钟×2）防止抖动反复横跳。

## 实测踩坑清单（new-api rc.44）

| 坑 | 结论 |
|---|---|
| 用账号密码做自动化 | 会话 15 分钟过期 + 每次登录留一条永不回收的会话记录，**50 条上限约 17 小时塞满，之后所有自动化 409 静默失败** → 用 PAT（见 02 篇） |
| 改渠道带 status 字段 | 服务器硬拒（400），**更新永不带 status** |
| status=3 | 系统保留值（自动禁用），人工 API 只能发 1/2 |
| 建渠道 body | 包裹形状 `{"mode":"single","channel":{...}}`；改是扁平对象且必须带 id |
| 渠道响应 | **永不回显 key 明文**，别指望读回来 |
| 「渠道测试」按钮失败 | **不写错误日志**，看门狗判据只吃真实转发流量 |
| 某出口全部模型卡死 | 别一轮测试就下结论——卡不卡是「模型×出口IP×时段」三维问题，换个出口可能就好 |

## 权限最小化

给自动化的 PAT 只勾需要的 scope：`channel:read/write/operate/sensitive_write`、`option:read/write`、`log:read`、`model:read`。
权限不够时接口会精确报缺哪个，按报错补即可。
