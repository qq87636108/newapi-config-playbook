# 精髓：多厂商 × 多账号 × 多模型 × 多服务器的配置经验

> 这套网关真实跑过：**十余家免费厂商、几十个账号、上百个模型条目、两台异地网关级联**。
> 本文不讲"New API 怎么点"，讲的是——当规模到「四多」交叉的程度，
> 为什么朴素配置法必然崩、以及扛住它的那套打法。全部来自实战，示例已脱敏。

## 0. 复杂度从哪来：四多矩阵

```
            厂商 A      厂商 B      厂商 C ...
账号 1   [模型a1,a2]  [模型b1]      [模型c1]
账号 2   [模型a1]     [模型b1,b2]   —
账号 3   —            [模型b2]      [模型c1,c2]
...
出口：主网关(出口IP-1) ⇄ 级联网关(出口IP-2,异地)
```

四多一交叉，问题性质就变了：

- 手工在面板上配，**几十上百条渠道**，改一个模型名要手动同步 N 处——改不动；
- 每个格子（厂商×账号×模型）健康状况**独立变化**：上午好的下午挂，A 出口好的 B 出口死；
- 出了故障，**不知道是哪一维的锅**——这是四多场景独有的难题。

所以整套装法，本质是给四个维度各配一件武器 + 一个交叉定位法：

| 维度 | 武器 | 一句话 |
|---|---|---|
| 多厂商 | 统一模型名 + 状态码映射 | 各家脾气不同，翻译成标准行为 |
| 多账号 | 账号×模型独立渠道 + 权重轮换 | 粒度细到格子，故障一眼定位 |
| 多模型 | 对号表 + 层级下探 + 别名告警 | 模型会消失会劣化，表是唯一真相 |
| 多服务器 | 级联网关 | 出口 IP 决定生死，别把鸡蛋放一个出口 |
| 四维交叉 | 矩阵思维排查法 | 固定三维测第四维 |

## 1. 多厂商：统一模型名 + 把各家翻译成标准行为

- **程序只认自定名**（model-1…），「统一模型名 → 厂商真实模型」的对号表是唯一真相；
  换厂商、加减账号只改表，调用方零改动；
- 各家错误行为不同：有的 429 限速、有的直接 502、有的**返回 200 但内容是死的**。
  用**状态码映射**（429→503）把"限速"翻译成"此渠道不可用"，让网关自动换下家；
- 参数差异（有的要额外 header/参数）尽量用**模型映射解决**，少用 header 覆盖——
  实测 param_override 会污染请求级快照，影响同一请求的后续渠道。

## 2. 多账号：粒度细到「账号×模型」一格

- **每个账号×每个模型一条独立渠道**——而不是"一个厂商一条大渠道"。
  这是多账号场景最重要的一条：免费账号的配额、限速、可用性都是**账号级独立**的，
  大渠道会把一个号的故障扩散到整条；
- 同厂商多账号：挂**同层级、按权重分流**（额度大的权重高）——等于免费容量叠加；
- 某号配额耗尽/被限 → 只有它那一格禁用，同层其他号无缝顶上，**用户无感**；
- 出故障时日志直接告诉你"厂商B·账号2·glm系模型 失败"，**不用猜是哪家哪号**。

## 3. 多模型：对号表 + 层级下探 + "别名 0 可用"告警

- 层级：main 主力（额度大速度快）→ backup → low；**同档不互兜**，重试按档位下探——
  同档互兜会循环重试放大故障（实测教训）；
- 同一统一名挂多个真实模型跨厂商——**模型会消失**：免费厂商的模型今天在明天没；
  必须监控「**别名下可用渠道数=0**」并告警，否则某天开始全体请求静默报错；
- 免费模型还有一个暗坑：**会劣化但不报错**——某账号×模型组合连续 24h 6/6 请求
  单次挂死 700-950 秒，HTTP 200"正常"。重试、自动禁用全都帮不上忙，
  只能人工移出候选；超时兜底要克制——加全局超时会掐断"慢但健康"的渠道、把流量推进有额度的备份层提前烧光（见 03 施工手册步骤 3）。

## 4. 多服务器：级联网关，出口即生命线

- 主网关把"另一台 New API"配成一个渠道，级联机器从**异地出口**打上游；
- **同一把 key、同一模型、同一请求体：出口 A 卡死（6/6 挂死），出口 B 秒回（0.7-4.4s）**——
  上游对来源 IP 的态度是三维问题（模型×出口IP×时段）；
- 所以多服务器不是可选项：**一个出口被上游"嫌弃"，换出口是唯一解**；
- 反过来也一样：某模型在两个出口全挂，才敢下结论"模型死了"，而不是"网络问题"；
- 级联机独立跑独立网关（独立端口、独立配置），主级之间靠统一模型名对齐语义。

## 5. 四维交叉：故障排查的矩阵思维

四多场景的故障，**永远先问"是哪一维的锅"**，方法是固定三维、单独测第四维：

| 症状 | 固定 | 单测 | 判定 |
|---|---|---|---|
| 某请求一直失败 | 换厂商账号 | — | 账号维的锅 |
| 某账号全部模型卡死 | 换模型再试 | 同号别家模型 | 账号/出口维的锅 |
| 某模型两个账号都挂 | 换出口（级联） | — | 模型维的锅 |
| A 出口全挂、B 正常 | — | 对比两出口 | 出口维的锅 |

两条铁律从矩阵里长出来：
1. **禁止单模型单轮次测试就给某出口/账号判死刑**（三维里可能只是"模型×出口×时段"恰好不利）；
2. **看门狗判据吃真实转发流量的错误日志**，不吃「渠道测试」按钮（实测测试失败不写日志）。

## 6. 让矩阵"活着"：自动化三件套

矩阵越大越管不动，所以三件自动化是四多规模下的必需品而非锦上添花：

1. **看门狗**：错误日志阈值（如 10 分钟 3 次）→ 自动禁用（status=3，与人工 2 区分，
   复活只认自己禁的）→ 复检退避 → 「别名 0 可用」「禁用超时」「脚本失败」全部告警外推（不许吞通知）；
2. **会话治理**：管理接口凭据用 PAT，不用账密会话（15 分钟过期 + 50 条上限 17 小时塞满，
   全部自动化 409 静默失败——真实事故）。创建配方见 02 篇；
3. **配置即文件**：对号表/渠道全部沉淀为 routing.yaml 版本化，改动=改文件+下发+可回滚；
   备份必须含配置与脚本本体，定时校验配置新鲜度防"改了没下发"。

## 7. 踩坑总表（速查）

| 坑 | 一句话结论 |
|---|---|
| 手工面板配几百条渠道 | 必然失控，配置即文件 |
| 一个厂商一条大渠道 | 故障扩散，必须账号×模型细粒度 |
| 同档重试互兜 | 循环放大故障，按档位下探 |
| 429 直接当失败 | 映射成 503 换渠道 |
| 模型悄悄下架 | 别名 0 可用必须告警 |
| 200 但内容是死的 | 只能人工移出候选+全局超时 |
| 单出口判死刑 | 三维问题，固定三维再测 |
| 渠道测试按钮 | 失败不写日志，看门狗看不见 |
| 账密做自动化 | 17 小时死，用 PAT |
| 改渠道带 status / status=3 | 硬拒 / 系统保留值 |
| 裸奔开注册 | 两天被自动注册 11 个用户 |
