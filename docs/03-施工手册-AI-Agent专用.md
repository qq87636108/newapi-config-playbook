# 施工手册：AI Agent 照此为用户配好 New API

> 写给 AI Agent 的执行清单。前两篇（01 思路 / 02 PAT 配方）讲"为什么"，
> 本篇讲"怎么做"：每步给到字段级，照序执行，最后过验收清单。
> 执行约定：**向用户要的只有三样**——服务器 SSH/面板访问、管理员账号、各家 API key；
> 涉及删除/覆盖操作先向用户确认。

## 步骤 0：部署网关

```bash
docker run -d --name new-api -p 3000:3000 \
  -v /opt/new-api/data:/data \
  calciumion/new-api:latest
```

- 首个注册用户即管理员——**装完立刻注册**，然后马上做步骤 1；
- 数据目录必须挂 volume（升级不丢配置）。

## 步骤 1：安全设置（不做的代价是真实事故）

面板 → 设置 → 运营/系统：

| 项 | 值 | 为什么 |
|---|---|---|
| 允许新用户注册 | **关闭** | 实测公网裸奔两天被自动注册 11 个账号 |
| 新用户初始额度 | 0 | 同上，双保险 |

## 步骤 2：拿管理凭据（PAT，给后续自动化用）

按 [02-PAT三步配方](02-PAT三步配方.md) 三步创建，scope 最小集：
`channel:read/write/operate/sensitive_write, log:read, option:read/write, model:read`。
把 `nap_` token 交给用户妥善保存——之后看门狗等自动化全用它。

## 步骤 3：系统选项（字段级）

面板 → 设置 → 其他/监控：

| 选项 | 值 | 说明 |
|---|---|---|
| `RetryTimes` | **3** | 失败重试次数；重试只在**同层级下探**，不要跨层互兜 |
| `AutomaticDisableStatusCodes` | **`401,402,403`** | **刻意不含 429**（瞬时限流，禁了可惜）；其余错误码靠日志关键字兜 |
| 流式/超时类全局参数 | 保持默认 | **不要加全局请求超时**来治"慢"——慢渠道被掐断会把流量推进有每日额度的备份层，提前烧光额度 |

## 步骤 4：和用户一起规划对号表（本手册的核心动作）

引导用户回答四个问题，产出一张表（**这张表是整个体系的唯一真相**）：

| 统一模型名 | 厂商 | 厂商真实模型 | 账号 | 层级 | 权重 |
|---|---|---|---|---|---|
| model-1 | 厂商A | their-fast-model | 账号1 | main | 100 |
| model-1 | 厂商A | their-fast-model | 账号2 | main | 60 |
| model-1 | 厂商B | glm-fast | 账号3 | backup | 50 |

1. 你常用哪些模型？（先列真实模型）
2. 每家注册了几个账号？各送多少额度？
3. 哪个模型你最常用 → 给 main 层；其余依次 backup/low；
4. 有没有异地服务器可以当级联出口？（有 → 该厂商渠道也可走级联，见步骤 5 红线）

## 步骤 5：建渠道（表里每行一条）

面板 → 渠道 → 添加，**每行一条**（账号×模型粒度，不要合并）：

| 字段 | 填法 |
|---|---|
| 名称 | `厂商-账号N-真实模型`（故障时一眼定位） |
| 类型 | 按厂商选 |
| 代理/Base URL | 厂商地址（走级联则填级联网关地址） |
| 密钥 | 该账号 key |
| 模型 | 勾选**该厂商真实模型** |
| 模型重定向 | `{"统一模型名":"真实模型"}` ——程序侧只发统一名 |
| 优先级 | main=100 / backup=50 / low=10（数字大的先被选中） |
| 权重 | 同优先级内按额度比例分 |
| 自动禁用 | 默认开；**若该渠道"慢但健康"总被测试误判** → 关掉（auto_ban=0），交给看门狗按真实错误码处理 |

## 步骤 6：验证（每条都要过）

```bash
curl http://<网关>:3000/v1/chat/completions \
  -H "Authorization: Bearer <用户令牌>" -H "Content-Type: application/json" \
  -d '{"model":"model-1","messages":[{"role":"user","content":"hi"}],"max_tokens":5}'
```

- 统一名能通 = 模型重定向生效；
- 故意填错某账号 key 重发 → 应自动换到同层其他渠道 = 兜底生效；
- 别名下可用渠道数 ≥1 逐个别名确认。

## 步骤 7：看门狗（Agent 按此规格写脚本，约百行）

规格（不可省略项）：
- 周期 5 分钟；凭据用步骤 2 的 PAT；判据 = `GET /api/log/` 错误日志（**不用**渠道测试接口）；
- 窗口 10 分钟内同渠道失败 ≥3 次 → `PUT` 渠道 status=**3**（自动禁用，与人工的 2 区分）；
- 复活：只恢复**自己禁的**，人工禁用的永不碰；复检退避 30 分钟起步、连续失败翻倍；
- 告警外推（如 Telegram）：别名可用渠道数=0 / 禁用超时未恢复 / 脚本自身失败都要推，**不许吞通知**；
- 工程要求：状态文件原子写 + `flock` 单实例锁。

## 步骤 8：验收清单（全打勾才算交付）

- [ ] 新用户注册已关闭
- [ ] PAT 已创建且 12 项管理路由可用（或至少 channel 读写+日志读）
- [ ] RetryTimes=3、AutomaticDisableStatusCodes=401,402,403
- [ ] 对号表已与用户逐行确认并留档
- [ ] 每条渠道命名=厂商-账号N-真实模型，模型重定向=统一名
- [ ] 每个别名 curl 通；坏 key 自动兜底验证过
- [ ] 看门狗在跑且 TG 告警收到过测试消息
- [ ] 备份：对号表/routing 配置/脚本本体已备份

## 红线（任何时候不许做）

1. **用户约定的模型映射/渠道清单不许删改**——只上报问题让用户定；坏上游交给自动禁用，不是去编辑配置；
2. 慢 ≠ 禁：只有真实错误码（401/403…）才禁用，超时/卡死只告警；
3. 单模型单轮次测试禁止给出口/账号判死刑（模型×出口IP×时段三维问题）；
4. 改渠道不带 status 字段；status=3 是系统保留值。
